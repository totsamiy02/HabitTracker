# Правила разработки HabitTracker

Применяй эти правила при работе над HabitTracker. Отвечай по-русски, важные технические решения объясняй простыми словами. Различай обсуждение и реализацию. Во время обсуждения предлагай варианты и готовь запрошенные макеты. Код приложения меняй по явной просьбе.

## 1. Контекст, документация и версии

- Перед работой прочитай [PROJECT.md](PROJECT.md) и изучи существующую реализацию в Android Studio. Сверяй реализованные возможности с кодом и тестами. Проектные решения помечай как планы, пока их нет в коде.
- При изменении поведения, пользовательского сценария, модели данных, правил безопасности, архитектуры или выпуска обнови соответствующий раздел `PROJECT.md` в той же задаче. Заменяй устаревшие сведения на месте и удаляй дубли. Косметические правки без изменения решений обычно не требуют обновления.
- Держи сводку короткой. Сохраняй правила работы, ограничения и расположение важных компонентов. История задач, коммиты, логи, результаты отдельных прогонов и временные пути в сводку не входят.
- Историю опубликованных версий веди в [CHANGELOG.md](CHANGELOG.md). Для релиза из `main` указывай дату, `versionName`, `versionCode`, ссылку на GitHub Release и пользовательские изменения. Рабочие изменения идут в `dev`. Когда пользователь просит закоммитить готовую версию, доведи её до выпуска. После локальных проверок отправь коммит в `dev` и дождись успешного GitHub Actions. Затем отправь тот же коммит в `main`, дождись подписания и проверь, что APK доступен в GitHub Releases.
- Храни временные макеты и скриншоты за пределами проекта. Для обсуждения давай путь к файлу. В контексте сохраняй принятые решения по дизайну.

## 2. Kotlin, Compose и архитектура

- Используй текущий стек и соглашения проекта. Основное приложение состоит из одного Android-модуля. Группируй экран, состояние и работу с данными по назначению. Разделяй правила выполнения привычек, хранение в Room, настройки в DataStore и отображение в Compose.
- Используй осмысленные имена, идиоматический Kotlin, понятное форматирование и короткие функции с ясной ответственностью. Многооперационные условия, обработчики и асинхронные цепочки оформляй многострочно, когда это помогает чтению. Простое выражение может оставаться однострочным.
- Переиспользуй подходящие модели, DAO, компоненты Material 3 и существующие тестовые средства. В затронутой области убирай устаревший код. Сохраняй действующие сценарии и совместимость данных. Добавляй слой или зависимость, только когда они решают конкретную задачу.
- Учитывай жизненный цикл Android и отмену корутин. Держи операции с данными вне отрисовки, не блокируй главный поток, обрабатывай ошибки и прерывания. Повторное действие пользователя и восстановление состояния должны оставлять данные согласованными.
- Храни ежедневные результаты независимо от способа рисования. Одна привычка получает максимум одну клетку на выполненный день. Изменение истории пересчитывает результат. Сессия таймера должна сохраняться ровно один раз, включая завершение в фоне.

## 3. Данные, секреты, резервные копии и обновления

- Основные сценарии работают офлайн. Для публичных GitHub Releases используй публичное чтение. Приватные токены, API-ключи и пароли подписи не встраивай в исходники, ресурсы, APK и логи.
- Держи релизный ключ и резервную копию ключа вне репозитория. Для CI используй GitHub Secrets. Перед коммитом проверяй индекс Git. Правила `.gitignore` применяются к неотслеживаемым файлам. Если секрет уже попал в репозиторий, сообщи о необходимости его отозвать или заменить. Значение секрета в ответе не цитируй.
- Используй системный выбор файлов для экспорта и восстановления. Копия содержит версию формата. Перед восстановлением проверь весь файл и покажи, что будет заменено. После подтверждения выполняй замену атомарно. Ошибка не должна портить текущие данные.
- Для обновления используй тот же `applicationId`, тот же ключ подписи и возрастающий `versionCode`. Установку подтверждает пользователь через Android. Изменения схемы Room сопровождай миграциями, сохраняющими данные. Исключи разрушительный сброс базы при обновлении.
- Используй синтетические данные для тестов. Личные базы, экспортированные копии и ключи подписи не направляй в тесты или публичный Git.

## 4. Интерфейс Android

- Следуй согласованной палитре «Слива и лаванда» и Material 3. Используй общую тему для цветов, типографики и форм. Чётко выделяй основное действие. Новые вкладки добавляй по мере появления соответствующего сценария.
- Перед изменением экрана изучи текущие компоненты и макеты. Используй согласованный русский интерфейс, храни пользовательские строки и форматы в ресурсах. Проверяй длинные названия, переносы, состояния пустого списка, загрузки, ошибки и завершения операции там, где они возникают.
- Учитывай небольшие экраны Android, системные панели, появление клавиатуры и увеличенный шрифт. Давай элементам удобные области нажатия и понятные семантические подписи для TalkBack. В мозаике предоставляй текстовый счётчик и доступное действие «Отметить сегодня».
- Сохраняй читаемость и контраст во всех темах, которые уже поддерживает приложение. Используй короткую анимацию только там, где она объясняет изменение состояния. Проверяй доступные состояния через Compose Preview или на телефоне, если он доступен для ручной проверки.

## 5. Тестирование и завершение задачи

- Самостоятельно оценивай, какие проверки нужны. Для изменений важных правил добавляй или обновляй тесты, которые ловят реальные регрессии. Цвета, отступы и статический текст обычно покрываются визуальной проверкой.
- Локальные JVM-тесты подходят для расчёта дневного прогресса, роста мозаики, времени таймера и проверки формата копии. Интеграционные Android-тесты подходят для Room, миграций, транзакций и записи сессий. Compose UI-тесты используй для важных сценариев, если существующая инфраструктура их поддерживает.
- Проверяй характерные ошибки. Повторная отметка в тот же день оставляет одну клетку. Невалидная копия оставляет базу в исходном состоянии. Обычное подписанное обновление сохраняет привычки, историю и прогресс. Для тестов времени используй управляемый источник времени и ожидание состояния.
- Используй Gradle Wrapper. Для функциональных изменений запускай относящиеся к задаче тесты, сборку и настроенный линтер по необходимости. Используй существующий GitHub Actions после его настройки. Сохраняй действующие проверки CI.
- Пользователь собирает APK на Mac и переносит на телефон вручную. USB и эмулятор не требуются. Проверку установки поверх предыдущей подписанной версии фиксируй отдельно от сборки и автоматических тестов.
- В конце кратко укажи, что изменилось, какие проверки действительно запускались и какие важные сценарии остались непроверенными. Если собран APK, укажи полный путь и короткий способ ручной проверки.
